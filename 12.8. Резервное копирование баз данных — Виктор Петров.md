\### Задание 1. Резервное копирование

\*\*Финансовая компания решила увеличить надёжность работы баз данных и их резервного копирования. Необходимо описать, какие варианты резервного копирования подходят в заданных случаях.\*\*



\#### Решение:



1\. \*\*1.1. Восстановление данных в полном объёме за предыдущий день:\*\*

&#x20;  \* \*\*Подходящий метод:\*\* Ежедневное \*\*полное резервное копирование (Full Backup)\*\*.

&#x20;  \* \*\*Описание:\*\* Раз в сутки (обычно в ночное время, когда нагрузка на систему минимальна) создается полный дамп всей базы данных. Если в течение дня происходит сбой, БД восстанавливается из ночной копии, возвращая состояние системы на конец предыдущего дня.



2\. \*\*1.2. Восстановление данных за час до предполагаемой поломки:\*\*

&#x20;  \* \*\*Подходящий метод:\*\* Сочетание ежедневного \*\*полного бэкапа\*\* и регулярного \*\*инкрементного копирования\*\* (либо бэкапа журналов транзакций / WAL / Binlog) каждый час.

&#x20;  \* \*\*Описание:\*\* Полная копия создается раз в сутки. Каждый час запускается инкрементный бэкап, который сохраняет только изменения, произошедшие за последние 60 минут. При сбое сначала разворачивается последний полный бэкап, а затем на него последовательно накатываются часовые инкременты до момента аварии.



3\. \*\*1.3.\* Моментальное переключение на работающую базу данных:\*\*

&#x20;  \* \*\*Ответ:\*\* \*\*Да, такой кейс возможен.\*\*

&#x20;  \* \*\*Описание:\*\* Для реализации мгновенного переключения (Failover) настраивается кластер высокой доступности (HA) с использованием \*\*синхронной или асинхронной репликации (Master-Slave)\*\*. Специализированное ПО автоматизации (например, \*Patroni\*, \*Keepalived\* или \*MHA\*) непрерывно мониторит состояние основного сервера. При его поломке трафик приложения за несколько секунд автоматически перенаправляется на актуальную Slave-реплику, которая становится новым Master-сервером.

\### Задание 2. PostgreSQL



\#### Решение:



1\. \*\*2.1. Примеры команд резервирования данных и восстановления БД:\*\*

&#x20;  

&#x20;  \* \*\*Резервное копирование (создание сжатого дампа в кастомном формате):\*\*

&#x20;    ```bash

&#x20;    pg\_dump -U postgres -h localhost -F c -b -v -f "backup\_lecture\_12\_8.dump" my\_database

&#x20;    ```

&#x20;    \* \*Пояснение флагов:\* `-U` — пользователь, `-h` — хост, `-F c` — кастомный сжатый формат файла, `-b` — включение больших объектов, `-v` — подробный вывод логов, `-f` — имя итогового файла.



&#x20;  \* \*\*Восстановление базы данных из созданного дампа:\*\*

&#x20;    ```bash

&#x20;    pg\_restore -U postgres -h localhost -d my\_database -v "backup\_lecture\_12\_8.dump"

&#x20;    ```

&#x20;    \* \*Пояснение флагов:\* `-d` — имя целевой базы данных, в которую будут развернуты данные.



2\. \*\*2.1.\* Автоматизация этого процесса:\*\*

&#x20;  \* \*\*Ответ:\*\* \*\*Да, автоматизация возможна и является стандартом.\*\*

&#x20;  \* \*\*Этапы выполнения автоматизации:\*\*

&#x20;    1. Создается скрипт автоматизации (Bash-скрипт для Linux или PowerShell для Windows), содержащий команду `pg\_dump`.

&#x20;    2. Настраивается беспарольный доступ утилиты к СУБД с помощью переменной окружения `PGPASSWORD` или конфигурационного файла `.pgpass`.

&#x20;    3. Скрипт добавляется в системный планировщик задач. В Linux используется планировщик \*\*Cron\*\* (например, запись `0 3 \* \* \* /scripts/pg\_backup.sh` будет запускать бэкап ежедневно в 3:00 ночи).

&#x20;    4. В скрипт добавляется логика ротации (автоматического удаления бэкапов старше N дней), чтобы не переполнять дисковое пространство.

&#x20;    5. Для крупных проектов используются готовые утилиты автоматизации корпоративного уровня: \*pgBackRest\* или \*Barman\*.

\### Задание 3. MySQL



\#### Решение:



1\. \*\*3.1. Пример команды инкрементного резервного копирования базы данных MySQL:\*\*

&#x20;  \* На практике для физического инкрементного копирования MySQL используется утилита \*\*Percona XtraBackup\*\*:

&#x20;  

&#x20;  \* \*\*Этап 1: Создание базового (полного) бэкапа:\*\*

&#x20;    ```bash

&#x20;    xtrabackup --backup --target-dir=/var/backups/base\_backup

&#x20;    ```

&#x20;  \* \*\*Этап 2: Создание инкрементного бэкапа (копируются только изменения относительно базового):\*\*

&#x20;    ```bash

&#x20;    xtrabackup --backup --target-dir=/var/backups/inc\_backup --incremental-basedir=/var/backups/base\_backup

&#x20;    ```

&#x20;  \* \*(Альтернативный логический метод — это регулярное копирование бинарных логов \*\*Binary Logs / binlog\*\*, куда MySQL записывает все транзакции).\*



2\. \*\*3.1.\* В каких случаях использование реплики будет давать преимущество по сравнению с обычным резервным копированием:\*\*

&#x20;  \* \*\*Минимальное время простоя (RTO близко к 0):\*\* Развертывание базы данных из файла бэкапа большого объема может занять часы. Реплика — это уже запущенный рабочий сервер, переключение на который происходит мгновенно при падении основного.

&#x20;  \* \*\*Перенос нагрузки со стандартных бэкапов:\*\* Процесс резервного копирования нагружает дисковую подсистему и процессор. Снятие бэкапов можно настроить со Slave-реплики, полностью освободив ресурсы основного продакшн-сервера (Master).

&#x20;  \* \*\*Географическое распределение (Disaster Recovery):\*\* Реплика может физически находиться в другом дата-центре или даже в другой стране. Если основной дата-центр будет обесточен или уничтожен, реплика позволит мгновенно восстановить бизнес-процессы.

&#x20;  \* \*\*Полезное использование ресурсов:\*\* В отличие от бэкапа, который просто лежит на диске, реплику можно использовать в повседневной работе для обработки тяжелых SELECT-запросов на чтение, построения аналитики и отчетов.
